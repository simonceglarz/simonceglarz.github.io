STM32 flight controller

Quadrotor flight-controller firmware on an STM32F446 (Cortex-M4F, 180 MHz) under FreeRTOS, reading an LSM6DSOX IMU over SPI. I wrote the requirements before measuring anything, and every timing number on this page comes from a logic-analyzer capture.

Status, October 2026: the firmware, the PC simulation and the hardware-in-the-loop rig all work on the bench. There are no motors yet, and it has not flown.

Requirements first

Before taking a single measurement I wrote six requirements (REQ-01 to REQ-06) in docs/requirements.md. REQ-01 originally asked for a 1 kHz loop. The IMU only offers 833 Hz or 1.66 kHz output rates, so I revised it to 1.66 kHz in its own documented commit rather than quietly changing the target. REQ-01 is now marked met, with the capture that proves it.

Timing, measured

The control task wakes on the IMU’s data-ready interrupt, so the loop runs at the sensor’s rate instead of a timer that could drift against it. A GPIO goes high at the start of each iteration and low at the end. On the logic analyzer that pin gives the loop period and execution time directly, and its offset from the interrupt line gives the latency.

The sensor runs 3.5% slow, on purpose

The loop measured 1.608 kHz, not the 1.666 kHz the datasheet lists. The LSM6DSOX has a factory trim register, INTERNAL_FREQ_FINE, that records each chip’s actual oscillator offset. This one reads −24, which works out to −3.60%. My measurement was −3.48%, within one register step (0.15%). The filter now reads that register at boot and computes its time step from it, instead of assuming the nominal rate.

Debugging: a 3.5 ms logging stall

The capture showed gaps in the loop pin, about five missing samples, repeating every ~105 ms. That interval matched the telemetry rate, not anything in the control path. The logging task runs at low priority, but it held a C-library lock for the 3.5 ms a UART line took to send, and the high-priority control task blocked on that same lock. Moving the formatting and transmission outside the lock removed the gaps. Task priority only protects you while the scheduler is free to switch tasks.

Debugging: a 1.7° offset at rest

With the board flat, the filtered angle sat 1.7° away from the accelerometer’s. Before reading any code, I estimated what gyro bias would cause it: about 3.6 °/s times the filter’s 0.47 s time constant, which matched within 0.1°. The calibration printout then showed −2.8 to −3.1 °/s against a true bias of +0.54 °/s. Calibration was running while the sensor was still settling after power-on. A settle delay, discarded first samples and a spread printout fixed it.

One control library, three places it runs

The PID controller (anti-windup, derivative on measurement, low-pass filtered D term), the complementary filter and the IMU unit conversion live in one C source tree that compiles for both the STM32 and the PC. That lets the same code run in three places:

  • Host unit tests. 43 tests through make test with -Werror: PID 7, complementary filter 8, IMU conversion 11, cascade 5, protocol 12.
  • Software-in-the-loop. A Python roll-axis simulator calls the firmware’s own pid.c through ctypes, using the measured loop rate and sensor noise. In simulation, a 10° step settles to ±1° in 245 ms with 0% overshoot. Under a constant 20% torque disturbance the angle stays 4° off without an integrator and recovers within about 0.3 s with one. The plant’s inertia, motor lag and thrust are estimates, so these are results against a model, not a drone.
  • Hardware-in-the-loop. The STM32 runs the cascaded controller while the Python plant sends it simulated sensor values over UART, in lock-step. I wrote a binary protocol (sync bytes, sequence number, CRC-16/CCITT-FALSE) once in C and once in Python and checked they produce identical bytes. Over 2,412 steps the board’s outputs matched the simulation bit for bit.

Not done yet

  • No motors or ESCs, and no flight.
  • Watchdog and failsafe behavior (REQ-02 to REQ-05), including the HIL fault test.
  • Control is single-axis (roll) in simulation; there is no 3-axis attitude estimate yet.
  • The barometer and magnetometer are bought but not integrated.
  • No custom PCB for this project yet.
